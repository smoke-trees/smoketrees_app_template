# Dart Analyze Report & Template Handling Guide

## Overview

The Mason brick template generates **413 warnings/info notices** from `dart analyze`, which is expected because:

1. **Template files use Jinja2 conditionals** - Mason uses `{% if %}...{% endif %}` syntax which is not valid Dart syntax
2. **Generated files are missing** - `.g.dart` files will be created by `build_runner` post-generation
3. **Style issues** - Many are linter suggestions (prefer single quotes, make variables final, etc.)

## Critical Errors During Generation (Will Be Fixed by Mason)

These errors only appear during analysis of the template source and will be **automatically resolved** when Mason generates the actual project:

### 1. Template Conditionals in `init_bindings.dart`
```dart
{%- if include_network_layer %}
import '../core/controllers/user_controller.dart';
{%- endif %}
```
**Status**: ✅ Will be removed or kept based on `include_network_layer` variable

### 2. Missing Generated Files
Files with `part 'xxx.g.dart'` declarations won't have those files during template analysis.
**Status**: ✅ Will be generated by `dart run build_runner build` after project generation

### 3. Package Import Templates
```dart
import 'package:{{project_name}}/utils/console_logger.dart';  // WRONG in template
import '../../utils/console_logger.dart';  // ✅ FIXED - relative import
```
**Status**: ✅ Fixed - now using relative imports

## How the Workflow Works

### 1. Template Phase (Current)
```
dart analyze __brick__/lib  # Shows warnings due to template syntax
```
Some warnings are expected and harmless.

### 2. Generation Phase (After User Runs `mason make`)
```bash
mason make smoketrees_app \
  --project_name my_app \
  --organization com.example \
  --app_name "My App"
```

Mason processes the template and:
- Removes `{% if %}` blocks based on variables
- Replaces `{{project_name}}` with actual values
- Creates valid Dart files

### 3. Post-Generation Phase (User runs in generated project)
```bash
cd my_app
flutter pub get
dart run build_runner build --delete-conflicting-outputs  # Generates .g.dart files
dart analyze lib  # Now shows 0 errors
```

## Why We Don't Fully Fix Template Analysis

Templates inherently have syntax that pre-processors understand but static analyzers don't. Common approaches:

1. **Accept warnings** (Current approach) - Most practical for templates
2. **Use analysis_options.yaml to ignore patterns** - Can suppress template-specific warnings
3. **Separate template and generated code** - Overly complex for this use case
